목표 UX: 세션에서 슛을 여러 개 찍으면 전부 저장되고, 나중에 아무 슛이나 골라 궤적·슬로모·바디 메시로 다시 본다. 이 페이지는 그 그림의 어디까지가 지금 실제로 작동하는지의 장부다.

01흐름

킥 소리 감지 → 슛마다 자동 컷 (클립 + 사이드카) → 서버 분석 (궤적·컨택·밴드) → 슛별 영구 저장 → 숏 맵: 모든 슛의 arc 한 화면, 탭 = 하이라이트 → 숏 디테일: 이 슛의 3D 씬 · 영상 · 지표 └─ 리플레이 4종 ↓

세션이 끝나도 슛은 사라지지 않는다 — 서버에 없는 결과는 로컬 SQLite가 먼저 들고 있다가 동기화한다. 네트워크가 죽어도 세션은 산다.

02슛별 보기 — 요소별 장부

보기상태비고
궤적 다시 보기 (3D 씬)지금 됨숏 맵: 전체 arc 동시 표시 + 선택 하이라이트, 정지 카메라(촬영 각도 포즈). refuse된 슛은 곡선을 안 그림
원본 리플레이지금 됨숏 디테일 영상 탭
슬로모 0.25×앱 작업 중같은 영상의 재생속도 제어 — 새 파일 불필요. 프레임 보간은 하지 않는다(보간 프레임 = 지어낸 데이터)
궤적 오버레이 영상앱 작업 중서버가 굽는 능력은 your-shot에서 증명됨 — 서빙 엔드포인트 + 앱 재생만
바디 메시 리플레이온디맨드 설계아래 03 참조 — 유일하게 자동이 아닌 조각

03바디 메시는 왜 "온디맨드"인가

메시 복원(GVHMR)은 슛당 GPU로 수 분이 걸린다. 모든 슛에 자동으로 돌리면 비용이 슛 수에 비례해서 커지므로, 설계는 반대로 간다:

보고 싶은 슛에서 버튼 → 렌더 → 완성되면 재생be-vision의 hero 상태기계가 이미 이 모양이다: none → rendering → ready | failed, 실패엔 이름 붙은 이유. 궤적·속도는 모든 슛에 즉시(CPU, 초 단위), 메시는 원할 때만(GPU, 분 단위) — 두 비용 곡선을 섞지 않는다.
남은 관문 둘① GPU 워커 — 프로토타입 셋업이 지금 진행 중. ② 라이선스 — SMPL-X는 연구용이라 개발 빌드까지만; 출시 전 상용 가능 바디로 교체(추적 중). 개발 중 메시 품질의 실물은 Your Mesh에 이미 있다.

04정직성이 리플레이에 남기는 것

  • 측정 안 된 슛의 곡선은 그리지 않는다 — refuse된 슛의 리플레이는 원본 영상뿐이다.
  • 슬로모는 스트레치지 보간이 아니다 — 없는 프레임을 만들어 넣지 않는다.
  • 메시 리플레이는 자기 상태를 말한다 — 렌더 중인지, 왜 실패했는지, 몸이 추정인지.
